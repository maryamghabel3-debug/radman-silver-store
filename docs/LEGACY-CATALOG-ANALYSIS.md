# تحلیل کاتالوگ عمومی فروشگاه قدیمی (`noghrehmashhad.ir`)

> تاریخ بررسی: `2026-08-20`<br>
> دامنه بررسی: فقط صفحات عمومی وب، `robots.txt` و Sitemapهای عمومی. هیچ API خصوصی، پنل مدیریت، credential یا مسیر ممنوع بررسی نشده است.

## ۱. خلاصه اجرایی

فروشگاه قدیمی یک کاتالوگ فارسی با URLهای پایدار از الگوی `/product/<id>/<slug>/` و `/category/<id>/<slug>/` دارد. صفحه هر محصول معمولاً عنوان، دسته، قیمت، چند تصویر، و مجموعه‌ای متغیر از مشخصات را نمایش می‌دهد. داده‌های وزن، عیار و سنگ برای بخشی از محصولات قابل مشاهده‌اند، اما پوشش و کیفیت آن‌ها یکنواخت نیست؛ بنابراین **استخراج عمومی فقط باید یک فایل پیشنهادی برای بازبینی مالک بسازد، نه import خودکار و قطعی**.

این مأموریت هیچ تصویر یا متن محصولی را دانلود/کپی نکرده است. تصاویر باید جداگانه توسط مالک و با احراز حق استفاده تهیه شوند.

### نکته مهم درباره taxonomy قدیمی

Sitemap دسته‌ها شامل ده‌ها زیرگروه سنگ و سبک است (عقیق سرخ/سبز/کبود، فیروزه، حدید، شجر، در نجف، الکساندریت، موزانایت، دست‌ساز، خطی و غیره). این‌ها نباید به‌عنوان دسته اصلی WooCommerce تکثیر شوند. پیشنهاد:

- دسته اصلی فقط یکی از `rings / necklaces / bracelets`؛
- نوع سنگ در `stone_type`؛
- جنسیت از SKU (`M/W/U`) و در آینده attribute؛
- سبک/حکاکی/رکاب پس از پاک‌سازی، به‌صورت attribute یا tag اختیاری.

## ۴. ساختار صفحه دسته

صفحات دسته معمولاً شامل موارد زیر هستند:

1. عنوان دسته و مرتب‌سازی (`جدیدترین` و فیلترهای قیمت/موجودی)؛
2. کارت محصول با تصویر thumbnail، عنوان، قیمت جاری، قیمت قبلی و درصد تخفیف؛
3. URL محصول با `product ID` عددی؛
4. JSON-LD از نوع `ItemList`/`Offer` برای بخشی از محصولات؛
5. وضعیت `InStock` در داده ساختاریافته، که لزوماً موجودی فیزیکی دقیق را ثابت نمی‌کند.

این صفحات برای **کشف URL و دسته اولیه** مناسب‌اند، اما برای وزن/عیار/سنگ باید صفحه خود محصول خوانده شود.

## ۵. ساختار صفحه محصول و فیلدهای قابل مشاهده

| فیلد | میزان دسترسی عمومی | نمونه/توضیح |
|---|---|---|
| product URL / internal ID | تقریباً همیشه | `/product/3639/...` |
| عنوان فارسی | همیشه | H1 و گاهی title مرورگر متفاوت |
| دسته و breadcrumb | معمولاً | انگشتر مردانه، دستبند مردانه، مدال یا گردنبند |
| برند | اختیاری | مانند `هخامنش` |
| شناسه کالا | متغیر و گاهی خراب | `1014`، `1199000`، یا مقدار اعشاری نامعتبر |
| قیمت جاری | معمولاً | نمایش فارسی/لاتین و گاهی JSON-LD |
| قیمت قبل/درصد تخفیف | اختیاری | روی کارت و صفحه محصول |
| وضعیت موجودی | در UI/Schema برای بعضی صفحات | نیازمند تأیید انسانی به‌دلیل پیام «استعلام موجودی» |

| تصاویر | معمولاً ۱ تا چند فایل | thumbnail و نمایش بزرگ از یک فایل با queryهای resize متفاوت |

### الگوی تصویر عمومی

فایل‌ها معمولاً در مسیر زیر دیده می‌شوند:

```text
/shop-resources/<store-id>/product-images/<timestamp>_<random>.<jpg|jpeg|png>
```

پارامترهای query مانند `?size=750x820&rs=fit` یا `?size=164x164&rs=fit` فقط renditionهای همان فایل‌اند. یک تصویر ممکن است چند بار در HTML تکرار شود (featured، gallery، thumbnail). URL تصویر برای تحلیل الگو مفید است، اما این toolkit عمداً آن را دانلود نمی‌کند.

## ۶. مشکلات کیفیت داده

1. **ارز و ضریب نمایش:** قیمت UI به تومان نمایش داده می‌شود، ولی JSON-LD بعضی صفحات `priceCurrency=IRR` دارد و مقدار آن ممکن است ۱۰ برابر عدد UI باشد. هیچ تبدیل خودکار از JSON-LD مجاز نیست؛ CSV مقصد مستقیماً تومان است.
2. **اعداد مخلوط:** ارقام فارسی، عربی و لاتین در یک عنوان/شناسه دیده می‌شوند (`9۲۵`، `10۶۲`).
3. **عنوان‌های ناسازگار:** در برخی صفحات title مرورگر، H1، alt تصویر و کد داخل متن با هم یکسان نیستند. برای نمونه صفحه محصول 3643 در title یک کد و در H1/تصویر کد دیگری نشان می‌دهد.
4. **شناسه کالای نامعتبر/تکراری:** بعضی شناسه‌ها اعشاری یا عمومی‌اند؛ نمونه‌های `1199000` بین چند محصول دیده می‌شوند. بنابراین SKU رادمان نباید مستقیماً از «شناسه کالا» بدون کنترل یکتایی ساخته شود.
5. **وزن ناقص:** وزن برای همه محصولات وجود ندارد؛ گاهی «تقریبی» است یا واحد ندارد. وزن نامطمئن باید به `legacy_mirror` یا `manual_locked` هدایت شود.
6. **سنگ و ارزش نگین:** نوع سنگ گاهی مشخص است، اما ارزش ثابت نگین عمومی نیست. `stone_value_toman` نیازمند ورود/تأیید مالک است.
7. **دسته آلوده:** دسته دستبند مردانه شامل زنانه، ست، چرم و تمام‌نقره است. دسته‌های سنگ نیز گاهی نتایج نامرتبط دارند.
8. **موجودی غیرقابل اتکا:** پیام سراسری «قبل از ثبت سفارش استعلام موجودی و قیمت بگیرید» با `InStock` عمومی تعارض عملیاتی دارد. موجودی باید 1:1 توسط مالک تأیید شود.
9. **توضیح تکراری یا عمومی:** بعضی توضیحات مقاله عمومی درباره نقره/خواص سنگ هستند و اطلاعات محصول خاص را تأیید نمی‌کنند؛ کپی مستقیم توصیه نمی‌شود.
10. **مدال در برابر گردنبند کامل:** برخی محصولات فقط آویز/مدال هستند. وجود زنجیر باید دستی تعیین شود.
11. **تصاویر تکراری و حق استفاده:** چند URL resize از یک فایل وجود دارد؛ مالک باید فایل اصلی و حق استفاده را تأیید کند.

## ۷. رویکرد پیشنهادی استخراج

### مرحله A — کشف عمومی و read-only

1. خواندن `sitemap-category.xml` و `sitemap-product.xml` با rate limit محافظه‌کارانه؛
2. استخراج URL، product ID، عنوان و دسته از HTML عمومی؛
3. استخراج JSON-LD فقط به‌عنوان evidence ثانویه، نه منبع نهایی ارز/موجودی؛
4. عدم ورود به مسیرهای منع‌شده robots و عدم استفاده از API خصوصی.

### مرحله B — نرمال‌سازی آفلاین

- تبدیل ارقام فارسی/عربی به لاتین برای فیلدهای عددی؛
- نگاشت فقط به سه دسته مصوب؛
- تشخیص تعارض عنوان/شناسه/قیمت؛
- نگه‌داشتن URL legacy به‌عنوان provenance در فایل کاری مالک (نه الزاماً محتوای عمومی)؛
- انتخاب pricing mode:
  - وزن معتبر و بدون ارزش سنگ: `silver_weight_only`؛
  - وزن معتبر + ارزش سنگ تأییدشده مالک: `silver_weight_plus_stone`؛
  - وزن نامطمئن + قیمت legacy تأییدشده: `legacy_mirror`؛
  - اثر خاص/دست‌ساز/قیمت کارشناسی: `manual_locked`.

### مرحله C — گیت انسانی

مالک باید پیش از import موارد زیر را تأیید کند:

- SKU یکتا، عنوان و دسته؛
- وزن **خالص نقره** (نه وزن کل همراه سنگ/چرم)؛
- نوع و ارزش نگین؛
- قیمت تومان برای حالت‌های legacy/manual؛
- موجودی واقعی 1:1؛
- متن محصول و مالکیت تصاویر.

### مرحله D — import امن

فایل تأییدشده به `RADMAN_PRIVATE_DIR/import/products.csv` منتقل و با `scripts/import_products.sh` ابتدا در حالت `--plan` بررسی می‌شود. apply فقط روی staging، پس از backup، و با ایجاد محصولات جدید در وضعیت Draft انجام می‌شود.

## ۸. تصمیم حقوقی/رسانه‌ای

- toolkit هیچ تصویر legacy را scrape/download نمی‌کند.
- URL عمومی تصویر در CSV پذیرفته نمی‌شود؛ فقط filename محلی پذیرفته می‌شود.
- مالک باید فایل‌هایی را که مالک آن‌هاست یا مجوز استفاده دارد در cPanel آپلود کند.
- متن توضیحات نیز باید بازنویسی/تأیید شود؛ متن عمومی legacy به‌طور خودکار کپی نمی‌شود.
